# 人力路線検索マスター

ランダムに与えられる2駅間について、実際の鉄道路線図を思い浮かべながら「経路（利用する路線と乗換駅）」を自分の頭で答えるブラウザゲームです。完全静的な SPA として実装されており、GitHub Pages 上でそのまま動作します。

## ゲーム概要

- 出題: ランダムな2駅間が示されるので、乗換駅と利用路線を答える。
- エリア: 東京23区内 / 東京都内 / 首都圏（Mini Tokyo 3D収録範囲） の3種類から選択可能。首都圏は収録されている全駅が対象。
- 難易度は2軸で独立に選べる。
  - 乗換回数: かんたん（乗換1回）/ ふつう（乗換1〜2回）/ むずかしい（乗換2回以上）。
  - 駅の規模（乗降客数）: 主要駅のみ / 中規模駅まで / 全駅。出発駅・到着駅の**両方**が条件を満たす。選んだエリア内の出題候補の乗換グループ（出題除外駅は除く）を乗降客数順に並べ、主要駅のみ = 上位20%、中規模駅まで = 上位60%、全駅 = すべて。乗降客数データのない駅は「全駅」でのみ出題される（割合は `src/lib/stationScale.ts` の定数）。
- 模範解答モード: 以下の2モードで「模範解答」となる経路が変わる。
  - 最短時間
  - 最小乗換回数
- 模範解答は**乗車券のみで乗れる列車（無料の列車）**で計算している。有料特急（ロマンスカー・成田エクスプレス・スカイライナー等）や座席指定ライナー（S-TRAIN・TJライナー・京王ライナー等）は使用しない。
- **直通運転（例: 副都心線→東急東横線→みなとみらい線）は乗換に数えない**。
- 経路探索・採点はすべてブラウザ内で完結する（サーバー通信なし）。

## 遊び方

トップ画面で「チャレンジモード」か「フリーモード」を選ぶ。

- **チャレンジモード**: 東京23区内・乗換1〜2回・最小乗換の固定条件で全10問に挑戦する。選べるのは難易度（かんたん=乗降客数上位50駅 / ふつう=上位100駅 / むずかしい=23区内の全駅）のみで、難易度は出題される駅の範囲を決める。1問ごとの結果は表示せず、10問終了後にまとめて「10問中N問正解」と称号（10問=人間路線検索エンジン / 8〜9=路線図の住人 / 5〜7=乗換上手 / 0〜4=迷子の旅人）を表示する。正解はパーフェクト判定のみで、経路が無効な場合も不正解として記録される。結果画面では各問をタップして自分の経路と模範解答を見られ、「Xでシェア」で結果を投稿できる。
- **フリーモード**: エリア・模範解答モード・乗換回数・駅の規模を自由に設定し、1問ずつ遊ぶ。連続正解・通算成績はフリーモードのみ集計される。

どちらのモードも経路の入力方法は共通。

1. 出題された出発駅・到着駅を確認する。
2. テキストボックスに路線名を入力するとオートコンプリートが表示されるので、現在の駅から乗る路線を選ぶ。漢字のほか、ひらがな・カタカナ・ローマ字（例: 「しんじゅく」「シンジュク」「shinjuku」）でも検索できる。
3. 続いて同じ路線上の降車駅（乗換駅、または最終的な到着駅）をオートコンプリートから選ぶ。同名の別の駅がある場合は、候補の横に乗り入れ路線名が表示される。
4. 到着駅に着くまで「路線を選ぶ→降車駅を選ぶ」を繰り返し、最後に解答を確定する。直通運転で乗り続ける場合の入力方法は下記「直通運転の入力方法」を参照（直通は乗換にならない）。
5. 模範解答と比較し、パーフェクト／おしい／不正解が判定される（フリーモードは1問ごとに表示）。

### 直通運転の入力方法

直通運転の列車にそのまま乗り続ける場合は、次のどちらの入力でもOK。どちらも乗換回数には数えない。

例: 永田町 → 三軒茶屋（半蔵門線から東急田園都市線へ直通）

- まとめて入力: 路線「半蔵門線」を選び、降車駅で「田園都市線直通」と添えられた「三軒茶屋」を選ぶ
- 分けて入力: 「半蔵門線」で永田町 → 渋谷、続けて「田園都市線」で渋谷 → 三軒茶屋

※ 降車駅の候補に「〇〇線直通」と書かれた駅は、選んだ路線の列車がそのまま乗り入れる駅。

## セットアップ

### 1. 依存関係のインストール

```bash
npm install
```

### 2. データ取得

本アプリのデータ源は次の2つです。

- [Mini Tokyo 3D](https://github.com/nagix/mini-tokyo-3d)（MIT License）: 路線・駅・時刻表
- [国土数値情報 駅別乗降客数データ（S12）](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-S12-2024.html)（国土交通省, CC BY 4.0）: 駅の規模（乗降客数）の絞り込み用。任意（無い場合は乗降客数なしでビルドされ、駅の規模は「全駅」のみ選べる）

Mini Tokyo 3D のデータは固定コミット（`fa7833f`）から必要なファイルをダウンロードします（約105MB、`data/mt3d/` に保存。`.gitignore` 済みでコミットしません）。

```bash
npm run fetch:mt3d
```

駅別乗降客数データ（約7MBのZIPからGeoJSONのみ展開、`data/s12/` に保存。`.gitignore` 済み）は次のコマンドで取得します。

```bash
npm run fetch:s12
```

各駅の乗降客数は最新の有効な年（データ無し・非公開・0の場合は前の年）の値を使い、駅名（表記ゆれを正規化）とホーム線形との距離（500m以内）、可能なら事業者の一致で Mini Tokyo 3D の駅に対応づけます。乗換グループの乗降客数は、対応づけた S12 レコード（重複掲載は1件に数える）の合計です。

取得するのは `railways.json` / `stations.json` / `station-groups.json` / `train-types.json` / `train-timetables/*.json` です。取得済みのファイルはスキップされるため、中断しても再実行で続きから取得できます（GitHub の raw.githubusercontent.com と API を使うだけで、有料サービスは不要です）。

### 3. network.json の生成

```bash
npm run build:network
```

`data/mt3d/` から `public/data/network.json`（Network v3、約0.7MB。S12 がある場合は各駅の `ridership` を含む）を生成します。このファイルは**リポジトリにコミットする運用**です（ビルド時に毎回生成し直すのではなく、手元で生成してコミットし、CIはコミット済みのファイルの存在チェックのみを行います）。

オプション:

```bash
npm run build:network -- --src <MT3Dのdataディレクトリ>   # data/mt3d/ 以外から読む
npm run build:network -- --fixture                        # リポジトリ同梱のミニデータ（MT3D形式）でビルド
```

### 4. 開発サーバー起動

```bash
npm run dev
```

`http://localhost:5173`（Vite のデフォルトポート）でゲームが起動します。

## 所要時間と乗換のモデル

### 所要時間（時刻表の最速基準）

駅間の所要時間は、MT3D が持つ**実際の時刻表（平日・土休日の両方）**から作ります。

1. 列車を「次の列車」リンク（`nt`）でつなぎ、物理的な1運用（run）にします（直通運転・分割併合も追従）。環状線（山手線）の周回の続きや、同じ駅の再訪になる連結は打ち切ります。
2. 同じ（停車駅, 区間の路線）の並びを持つ運用を1つの**パターン**（有向の停車駅列）にまとめ、**合計所要時間が最小の1運用**の時刻から区間所要秒を取ります（運用ごとに最小を拾うのではなく、1運用の実績をそのまま採用）。途中駅は出発時刻、終着駅は到着時刻で累積します。時刻は分単位なので1分の丸めがあります。
3. 他のパターンの連続部分列で、かつその区間の所要時間が同等以下のパターンは刈り込みます。
4. 山手線は方向ごとに、最速の1周列車から環状パターンを作ります（モジュラー走査で始点をまたぐ乗車も扱う）。

```
総所要時間 = パターン上の区間所要秒の合計 + 乗換回数 × 300秒（固定）
```

- 乗換ペナルティは1回あたり300秒（固定）です。同じ乗換グループ内（駅構内の乗り換え）でのパターンの乗り換えに加算します。
- 時計は持たない（待ち時間・本数は考慮しない）ので、「最速の列車にいつでも乗れる」前提の目安です。

### 直通運転は乗換ではない

- 1つのパターンに乗り続ける限り、路線をまたいでも1回の乗車で、乗換になりません（例: 池袋→元町・中華街は副都心線→東横線→みなとみらい線の直通で乗換0回）。
- 模範解答の経路は路線ごとに区間を分けて表示しますが、直通で続く区間には「直通」と表示します。
- 乗換 = パターンを乗り換えること。同じ路線の別の系統への乗り換えも乗換です（例: 大江戸線 新宿西口→練馬で都庁前で乗り換える場合）。
- プレイヤーの経路の採点も同じモデルで、区間の並びを実現する最良の乗り方（最短時間モード: 総所要時間最小、最小乗換モード: 乗換回数最小→総所要時間最小）で評価します。同じパターンのまま次の区間に続く場合は乗換になりません。

### 無料の列車のみ

乗車券のみで乗れる列車だけを使います。有料特急（JR東日本・東海、小田急、東武、西武、東京メトロ（ロマンスカー）、伊豆急・伊豆箱根・富士急、スカイライナー 等）と座席指定ライナー（モーニング/イブニングライナー、京王ライナー、TJライナー、THライナー、拝島ライナー、京急ウィング、S-TRAIN、JRのホームライナー 等）、有料の急行・観光列車・SL・バス代行は、`scripts/buildMt3dNetwork.ts` の `EXCLUDED_TRAIN_TYPES`（コメント付きの明示リスト）で除外しています。京急・京王・東急・京成・相鉄などの「特急」や、アクセス特急・快速特急・Fライナー等は追加料金不要なので使います。無料列車が1本もない路線（連絡線・貨物線・S-TRAIN専用の路線など）と、サービスのなくなった駅は路線・駅の候補から外れます。

### 乗換グループ

MT3D の `station-groups.json`（乗換駅の駅群）と各駅の `alternate` から同一グループを作ります。グループに載っていない駅は単独グループです。加えて、MT3D のグループに漏れていた「同名かつ250m以内」の駅も同一グループにします（例: 大江戸線の豊島園と西武豊島線の豊島園）。

## 乗換グループの調整

乗換グループ（同じ乗換駅として扱う駅の集まり）は Mini Tokyo 3D のデータから自動生成されますが、実態に合わない箇所を `data/transfer-group-overrides.json`（コミット対象）で手動調整できます。`npm run build:network` のビルド時に適用されます。グループは「駅名の集合」で指定し（挙げた駅名をすべて含むグループ）、該当が0件・複数件の場合や split で駅名が挙げ漏れている場合はビルドが失敗します。

- `split`: 該当グループ内で、挙げた駅名ごとに別の乗換駅に分割する（例: `["日比谷", "有楽町"]`）
- `merge`: 2つのグループを1つに統合する（`[["駅名A"], ["駅名B"]]` の組で指定）
- `exclude`: 該当グループ内の全駅を出題の出発駅・到着駅に使わない（`Station.noQuestion`）。経路の途中やオートコンプリートでは使える

判定の経緯は `docs/transfer-groups.md` を参照してください。

## 検証コマンド

```bash
npm test                       # ユニットテスト（Vitest）
npm run route -- 新宿 東京      # 実データでの経路探索を手元で確認するCLI
```

`route` コマンドの詳細:

```bash
npm run route -- <出発駅名> <到着駅名> [time|transfers]
```

- `public/data/network.json` を読み込み、指定した2駅間を実際に `searchRoute`（探索本体）で探索し、経路（路線・乗換駅・直通）・乗換回数・所要時間を表示します。
- モード（`time` または `transfers`）を省略すると両方のモードで探索します。
- 駅名は完全一致（NFKC正規化後）で検索します。同名の駅が複数のグループ（例: 別の場所にある同名の浅草）に存在するときは一意に決まらないため、候補一覧（駅名＋乗り入れ路線）を表示して終了します。

## アーキテクチャ概説

1. **MT3D データ → network.json（ビルド時）**
   `scripts/fetch-mt3d.ts` が固定コミットのデータを `data/mt3d/` に取得し、`scripts/build-mt3d-network.ts`（CLI）が `scripts/buildMt3dNetwork.ts`（純粋関数）で有料列車の除外・運用の連結・最速運用の選択・刈り込み・乗換グループ化を行い、`public/data/network.json`（Network v3）を生成します。
2. **データモデル（`src/lib/types.ts`）**
   `Network` は駅レコード（路線ごとに別レコード。`group` で乗換駅を束ねる）・路線・**パターン**（有向の停車駅列。`stops` / `segSec` / `segLine`）を持ちます。パターンは直通運転で路線をまたぐためトップレベルに置き、路線をまたぐ継ぎ目（駅レコードが変わるだけの接続）は `segLine = -1` の「直通リンク」区間（所要秒は次の出発 − 前の到着）です。環状パターンは `stops` の末尾に始点を再掲します。
3. **経路探索（Web Worker 内）**
   `src/lib/raptor.ts` の `searchRoute(network, from, to, mode)` が、「パターン上のある停車位置に乗っている」状態と「ある乗換グループにいる」状態を節点にした Dijkstra 法で、最短時間・最小乗換の経路を求めます（1回の探索は通常数十ミリ秒）。戻り値は `Itinerary`（`legs` / `rideSec` / `totalSec` / `transfers`）で、直通で続く区間には `through: true` が付きます。
4. **エリア判定**
   `src/lib/area.ts` が `src/data/areas.json`（東京23区・東京都のポリゴン）で point-in-polygon 判定します。首都圏エリアは全駅が対象です。
5. **出題・採点・表示整形**
   `src/lib/question.ts` が出題（パターン単位の乗換回数BFS）、`src/lib/validate.ts` が検証（`validateRoute`）と採点（`evaluateRoute`: 区間の並びを実現する最良の乗り方のDP）、`src/lib/game.ts` が表示用ヘルパーと判定、`src/lib/autocomplete.ts` / `src/lib/romaji.ts` が日本語・かな・ローマ字の検索を担当します。

## デプロイ

`main` ブランチへの push で GitHub Actions（`.github/workflows/deploy.yml`）が自動的に以下を実行し、GitHub Pages にデプロイします。

1. `npm ci`
2. `npm test`（失敗時はデプロイしない）
3. `public/data/network.json` の存在チェック（コミット漏れの検知。生成自体はCI上では行わない）
4. `npm run build`
5. GitHub Pages へアップロード・デプロイ
